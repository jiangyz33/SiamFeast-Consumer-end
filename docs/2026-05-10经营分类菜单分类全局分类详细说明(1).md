# 2026-05-10 经营分类、菜单分类、全局分类详细说明文档

## 1. 先给结论

当前系统里容易混淆的“分类”其实应该拆成三层：

| 名称 | 当前代码/字段 | 管理方 | 服务对象 | 页面位置 | 核心作用 |
|---|---|---|---|---|---|
| 经营分类 | `business_types` / `business_type` | 总控 | 平台、门店、C 端首页 | C 端首页入口、门店筛选、总控门店配置 | 定义门店经营什么业务 |
| 全局分类 | `menu_categories(store_id=0)`，菜品 `category_id` 引用它 | 总控 | 菜品标准归属、规则、报表、筛选 | 总控分类配置、菜品创建下拉 | 定义菜品属于哪类标准商品分类 |
| 菜单分类 | `store_menu_categories`，菜品 `store_menu_category_id` 引用它 | 门店 | 门店点餐页展示 | 进店点餐页左侧分类 | 定义门店自己的菜单展示分组 |

一句话：

| 类型 | 类比美团 | 举例 |
|---|---|---|
| 经营分类 | 商家经营品类 / 店铺品类 | 火锅、麻辣烫、海鲜面、民宿、咖啡 |
| 全局分类 | 平台商品类目 / 标准商品归属 | 火锅套餐、火锅计件、麻辣烫、饮品、早餐咖啡 |
| 菜单分类 | 商家菜单分组 | 招牌锅贴、热销套餐、营养汤粥、饮品饮料 |

## 2. 为什么必须拆成三层

如果只用一套分类，会出现三个问题：

| 问题 | 表现 | 后果 |
|---|---|---|
| C 端首页分类和进店点餐分类混用 | 首页展示“招牌锅贴、饮品饮料” | 用户不知道是在找店还是找菜 |
| 总控分类和门店自定义分类混用 | 门店改了分类名，平台规则跟着乱 | 优惠券、报表、拼团、搜索难以统一 |
| 菜品归属和页面展示混用 | 一个菜只能服务一个展示场景 | 门店无法灵活调整点餐页结构 |

正确拆分后：

| 层级 | 解决的问题 |
|---|---|
| 经营分类 | 用户要找什么类型的店，平台允许门店经营什么业务 |
| 全局分类 | 平台如何标准化管理菜品，规则和统计如何归类 |
| 菜单分类 | 门店点餐页面怎么排版，怎么让用户更容易点单 |

## 3. 经营分类

### 3.1 定义

经营分类是门店级的大业务类型，表示一家门店经营哪些业务。

例如：

| code | 名称 | 说明 |
|---|---|---|
| `HOTPOT_BUFFET` | 火锅自助 | 餐饮门店经营火锅自助 |
| `HOTPOT_PER_ITEM` | 火锅计件 | 按菜品计价的火锅 |
| `MALA_TANG` | 麻辣烫 | 麻辣烫业务 |
| `SEAFOOD_NOODLE` | 海鲜面 | 海鲜面业务 |
| `STANDARD_FOOD` | 标准餐饮 | 普通餐饮菜品 |
| `HOSTEL_ROOM` | 民宿房间 | 纯住宿业务 |
| `HOSTEL_COFFEE` | 民宿咖啡 | 民宿附带咖啡早餐 |
| `HOSTEL_HOTPOT` | 民宿火锅 | 民宿附带夜宵火锅 |

### 3.2 当前代码位置

| 对象 | 位置 | 说明 |
|---|---|---|
| 模型 | `internal/model/business_type.go` | `BusinessType` |
| 门店字段 | `stores.business_types` | JSONB 数组，一个门店可有多个经营分类 |
| 菜品字段 | `menu_items.business_type` | 单个菜品属于一个经营分类 |
| 总控路由 | `/api/v1/admin/business-types` | 总控管理经营分类 |
| C 端路由 | `/api/v1/business-types` | C 端读取经营分类入口 |

### 3.3 数据结构

```json
{
  "id": 1,
  "code": "HOTPOT_BUFFET",
  "name": "火锅自助",
  "name_en": "Hotpot Buffet",
  "name_th": "บุฟเฟต์หม้อไฟ",
  "icon_url": "https://cdn.example.com/icons/hotpot.png",
  "sort_order": 10,
  "is_active": true,
  "created_at": "2026-05-10T10:00:00+08:00",
  "updated_at": "2026-05-10T10:00:00+08:00"
}
```

### 3.4 总控端怎么用

总控端用于管理平台支持哪些经营业务。

| 操作 | 接口 | 说明 |
|---|---|---|
| 查看经营分类 | `GET /api/v1/admin/business-types` | 总控列表 |
| 新增经营分类 | `POST /api/v1/admin/business-types` | 新增平台业务类型 |
| 查看详情 | `GET /api/v1/admin/business-types/:id` | 查看单个经营分类 |
| 修改经营分类 | `PATCH /api/v1/admin/business-types/:id` | 改名称、图标、排序等 |
| 启用停用 | `PATCH /api/v1/admin/business-types/:id/status` | 控制是否可用 |
| 删除经营分类 | `DELETE /api/v1/admin/business-types/:id` | 建议只允许删除未被引用的非系统项 |

### 3.5 总控创建门店时怎么用

门店的 `business_types` 字段保存经营分类 code 数组。

请求示例：

```json
{
  "name": "曼谷金汤火锅·麻辣烫店",
  "business_types": ["HOTPOT_BUFFET", "MALA_TANG"],
  "status": "OPEN",
  "address": "曼谷拉抛区 Rama IX 88 号",
  "phone": "+66-80-010-0001"
}
```

含义：

| 字段 | 含义 |
|---|---|
| `HOTPOT_BUFFET` | 这个门店可以创建火锅自助类菜品 |
| `MALA_TANG` | 这个门店可以创建麻辣烫类菜品 |
| 不包含 `HOSTEL_ROOM` | 这个门店不是民宿门店，不能创建房型 |

### 3.6 门店端怎么用

门店创建菜品时，菜品的 `business_type` 必须在本门店 `stores.business_types` 里。

例如门店只开通：

```json
["HOTPOT_BUFFET", "MALA_TANG"]
```

那么菜品只能选择：

| 可选 | 不可选 |
|---|---|
| `HOTPOT_BUFFET` | `HOSTEL_ROOM` |
| `MALA_TANG` | `SEAFOOD_NOODLE` |

### 3.7 C 端怎么用

C 端首页和门店搜索页应该使用经营分类，而不是菜单分类。

| 页面 | 应使用接口 | 展示内容 |
|---|---|---|
| 首页业务入口 | `GET /api/v1/business-types` | 火锅、麻辣烫、海鲜面、民宿 |
| 门店筛选 | `GET /api/v1/stores?business_type=HOTPOT_BUFFET` | 展示开通该经营分类的门店 |
| 附近门店 | `GET /api/v1/stores/nearby?lat=...&lng=...&business_type=...` | 按距离和经营分类过滤 |

不要在 C 端首页拿 `GET /api/v1/categories` 做主入口。那是菜品分类，不是找店分类。

## 4. 全局分类

### 4.1 定义

全局分类是平台统一维护的菜品标准分类。它不是门店点餐页左侧菜单，也不是 C 端首页经营入口。

全局分类用于回答：这个菜品从平台规则上属于哪一类。

例如：

| 全局分类 | business_type | 说明 |
|---|---|---|
| 火锅套餐 | `HOTPOT_BUFFET` | 火锅自助类菜品标准分类 |
| 火锅计件 | `HOTPOT_PER_ITEM` | 按件火锅类菜品标准分类 |
| 麻辣烫 | `MALA_TANG` | 麻辣烫类菜品标准分类 |
| 海鲜面 | `SEAFOOD_NOODLE` | 海鲜面类菜品标准分类 |
| 民宿早餐咖啡 | `HOSTEL_COFFEE` | 民宿咖啡早餐类商品 |
| 民宿夜宵火锅 | `HOSTEL_HOTPOT` | 民宿火锅类商品 |

### 4.2 当前代码位置

| 对象 | 位置 | 说明 |
|---|---|---|
| 模型 | `internal/model/menu.go` | `MenuCategory` |
| 数据表 | `menu_categories` | `store_id=0` 表示全局分类 |
| 菜品字段 | `menu_items.category_id` | 当前实际等价于 `global_category_id` |
| 总控接口 | `/api/v1/admin/menu/categories` | 总控管理全局分类 |
| 门店查询接口 | `/api/v1/menu/categories` | 门店创建菜品时读取全局分类 |
| C 端查询接口 | `/api/v1/categories` 或 `/api/v1/public/categories` | 当前可查全局分类，但不建议作为首页主入口 |

### 4.3 数据结构

```json
{
  "id": 101,
  "store_id": 0,
  "name": "火锅套餐",
  "name_en": "Hotpot Set",
  "name_th": "ชุดหม้อไฟ",
  "icon_url": "https://cdn.example.com/categories/hotpot.png",
  "business_type": "HOTPOT_BUFFET",
  "sort_order": 10,
  "is_active": true,
  "source": "global",
  "created_at": "2026-05-10T10:00:00+08:00"
}
```

### 4.4 `store_id=0` 的含义

`menu_categories.store_id=0` 表示平台全局分类。

| store_id | 含义 | 当前建议 |
|---|---|---|
| `0` | 总控维护的全局分类 | 保留并作为菜品标准分类 |
| 大于 0 | 早期门店自建分类或历史数据 | 不建议继续作为菜品标准分类使用 |

### 4.5 总控端怎么用

| 操作 | 接口 | 说明 |
|---|---|---|
| 查看全局分类 | `GET /api/v1/admin/menu/categories` | 总控分类列表 |
| 按经营分类过滤 | `GET /api/v1/admin/menu/categories?business_type=HOTPOT_BUFFET` | 只看火锅自助分类 |
| 创建全局分类 | `POST /api/v1/admin/menu/categories` | 创建 `store_id=0` 分类 |
| 修改全局分类 | `PATCH /api/v1/admin/menu/categories/:id` | 改名称、图标、排序 |
| 删除全局分类 | `DELETE /api/v1/admin/menu/categories/:id` | 被菜品引用时应拒绝 |

### 4.6 门店端怎么用

门店创建菜品时必须选择全局分类。

菜品创建请求示例：

```json
{
  "name": "招牌牛肉火锅",
  "business_type": "HOTPOT_BUFFET",
  "category_id": 101,
  "store_menu_category_id": 8,
  "price": 299.00,
  "is_active": true
}
```

这里的字段含义：

| 字段 | 含义 | 是否必填 |
|---|---|---|
| `business_type` | 该菜品属于哪个经营分类 | 必填 |
| `category_id` | 该菜品属于哪个平台全局分类 | 必填 |
| `store_menu_category_id` | 该菜品在门店点餐页放到哪个菜单分组 | 建议必填 |

### 4.7 后端当前校验规则

代码位置：`internal/modules/catalog/service.go` 的 `validateItemClassification`。

| 校验 | 不通过错误 |
|---|---|
| `business_type` 不能为空 | `INVALID_BUSINESS_TYPE` |
| `business_type` 必须在经营分类表中启用 | `INVALID_BUSINESS_TYPE` |
| 门店必须开通该 `business_type` | `STORE_BUSINESS_TYPE_NOT_ENABLED` |
| `category_id` 必须存在 | `NOT_FOUND` |
| `category_id` 必须引用 `store_id=0` 的全局分类 | `CATEGORY_NOT_GLOBAL` |
| 全局分类 `business_type` 必须匹配菜品 `business_type` | `CATEGORY_BUSINESS_TYPE_MISMATCH` |
| `store_menu_category_id` 如果传入，必须属于当前门店 | `STORE_MENU_CATEGORY_NOT_FOUND` |

### 4.8 兼容规则

当前代码允许部分历史分类值兼容新经营分类：

| 旧分类值 | 可匹配的新经营分类 |
|---|---|
| `standard` | `STANDARD_FOOD`、`SEAFOOD_NOODLE` |
| `hotpot` | `HOTPOT_BUFFET`、`HOTPOT_PER_ITEM`、`HOSTEL_HOTPOT` |
| `malatang` | `MALA_TANG` |
| `coffee` | `HOSTEL_COFFEE` |
| `hostel` | `HOSTEL_ROOM` |

这只是兼容历史数据，不是长期推荐。长期应该统一使用经营分类 code，例如 `HOTPOT_BUFFET`。

## 5. 菜单分类

### 5.1 定义

菜单分类是门店自己的点餐页展示分组，类似美团进店点餐页面左侧的“招牌锅贴、推荐、饮品饮料、热销套餐”。

它只解决一个问题：门店点餐页怎么展示菜品。

### 5.2 当前代码位置

| 对象 | 位置 | 说明 |
|---|---|---|
| 模型 | `internal/model/business_type.go` | `StoreMenuCategory` |
| 数据表 | `store_menu_categories` | 门店菜单分类表 |
| 菜品字段 | `menu_items.store_menu_category_id` | 菜品绑定门店菜单分类 |
| 门店接口 | `/api/v1/store/menu-categories` | 门店管理自己的菜单分类 |

### 5.3 数据结构

```json
{
  "id": 8,
  "store_id": 1,
  "name": "招牌锅贴",
  "name_en": "Signature Potstickers",
  "name_th": "เกี๊ยวซ่าซิกเนเจอร์",
  "icon_url": "https://cdn.example.com/menu/signature.png",
  "sort_order": 10,
  "is_active": true,
  "created_at": "2026-05-10T10:00:00+08:00",
  "updated_at": "2026-05-10T10:00:00+08:00"
}
```

### 5.4 门店端怎么用

| 操作 | 接口 | 说明 |
|---|---|---|
| 查看本店菜单分类 | `GET /api/v1/store/menu-categories` | 进店点餐页左侧分类来源 |
| 新建本店菜单分类 | `POST /api/v1/store/menu-categories` | 门店自定义名称和排序 |
| 修改本店菜单分类 | `PATCH /api/v1/store/menu-categories/:id` | 改名称、图标、排序 |
| 删除本店菜单分类 | `DELETE /api/v1/store/menu-categories/:id` | 删除本店分类 |

创建请求示例：

```json
{
  "name": "招牌推荐",
  "name_en": "Signature",
  "name_th": "เมนูแนะนำ",
  "icon_url": "https://cdn.example.com/menu/signature.png",
  "sort_order": 10
}
```

返回示例：

```json
{
  "id": 8,
  "message": "created"
}
```

### 5.5 C 端进店点餐页怎么用

进店点餐页应该优先按门店菜单分类展示。

理想返回结构：

```json
{
  "store_id": 1,
  "categories": [
    {
      "id": 8,
      "name": "招牌推荐",
      "sort_order": 10,
      "items": [
        {
          "id": 1001,
          "name": "招牌牛肉火锅",
          "business_type": "HOTPOT_BUFFET",
          "category_id": 101,
          "store_menu_category_id": 8,
          "price": 299.00,
          "original_price": 329.00,
          "image_url": "https://cdn.example.com/items/beef-hotpot.png",
          "is_active": true,
          "is_sold_out": false
        }
      ]
    }
  ]
}
```

### 5.6 和全局分类的区别

| 对比项 | 全局分类 | 菜单分类 |
|---|---|---|
| 管理方 | 总控 | 门店 |
| 数据表 | `menu_categories` | `store_menu_categories` |
| 菜品字段 | `category_id` | `store_menu_category_id` |
| 是否全平台统一 | 是 | 否 |
| 是否影响报表规则 | 是 | 一般不影响 |
| 是否影响进店点餐页左侧展示 | 不建议直接影响 | 是 |
| 是否允许门店改名 | 不允许 | 允许 |

## 6. 三者完整关系

### 6.1 数据关系图

```text
business_types
  code = HOTPOT_BUFFET
       |
       | stores.business_types 包含 HOTPOT_BUFFET
       v
stores
  id = 1
       |
       | menu_items.store_id = 1
       v
menu_items
  business_type = HOTPOT_BUFFET
  category_id = 101
  store_menu_category_id = 8
       |                         |
       |                         v
       |                   store_menu_categories
       |                     id = 8
       |                     name = 招牌推荐
       v
menu_categories
  id = 101
  store_id = 0
  business_type = HOTPOT_BUFFET
  name = 火锅套餐
```

### 6.2 菜品创建时的完整链路

| 步骤 | 选择内容 | 数据来源 | 校验 |
|---|---|---|---|
| 1 | 选择经营分类 | 当前门店 `stores.business_types` | 必须已启用 |
| 2 | 选择全局分类 | `/api/v1/menu/categories?business_type=xxx` | 必须 `store_id=0`，且匹配经营分类 |
| 3 | 选择菜单分类 | `/api/v1/store/menu-categories` | 必须属于当前门店 |
| 4 | 填菜品信息 | 前端表单 | 价格、名称、图片等校验 |
| 5 | 提交菜品 | `POST /api/v1/menu/items` | 后端统一校验三类关系 |

### 6.3 示例

门店：曼谷金汤火锅·麻辣烫店

```json
{
  "store_id": 1,
  "business_types": ["HOTPOT_BUFFET", "MALA_TANG"]
}
```

可以创建的菜品：

| 菜品 | business_type | 全局分类 category_id | 菜单分类 store_menu_category_id | 是否合法 |
|---|---|---|---|---|
| 招牌牛肉火锅 | `HOTPOT_BUFFET` | 火锅套餐 | 招牌推荐 | 合法 |
| 麻辣烫荤菜套餐 | `MALA_TANG` | 麻辣烫 | 热销套餐 | 合法 |
| 海鲜面 | `SEAFOOD_NOODLE` | 海鲜面 | 主食 | 不合法，门店未开通海鲜面 |
| 牛肉火锅 | `HOTPOT_BUFFET` | 麻辣烫 | 招牌推荐 | 不合法，全局分类不匹配经营分类 |
| 牛肉火锅 | `HOTPOT_BUFFET` | 门店自建旧分类 | 招牌推荐 | 不合法，`category_id` 必须是全局分类 |

## 7. 三端页面应该怎么展示

### 7.1 总控端

| 页面 | 展示什么 | 使用接口 |
|---|---|---|
| 经营分类管理 | 火锅、麻辣烫、民宿等经营分类 | `/api/v1/admin/business-types` |
| 门店编辑 | 给门店勾选经营分类 | `/api/v1/admin/business-types`、`/api/v1/admin/stores/:id` |
| 全局分类管理 | 火锅套餐、麻辣烫、咖啡等标准菜品分类 | `/api/v1/admin/menu/categories` |
| 报表筛选 | 按经营分类、全局分类筛选 | `/api/v1/admin/reports/*` |

总控不应该管理门店菜单分类，除非做监管详情页。

### 7.2 门店端

| 页面 | 展示什么 | 使用接口 |
|---|---|---|
| 菜品创建 | 经营分类、全局分类、菜单分类三个下拉 | `/api/v1/menu/categories`、`/api/v1/store/menu-categories` |
| 菜单分类管理 | 本店左侧菜单分组 | `/api/v1/store/menu-categories` |
| 菜品列表 | 按菜单分类或经营分类筛选 | `/api/v1/menu/items` |
| 纯民宿门店 | 不展示餐饮菜单分类 | 根据 `business_types` 判断 |

门店不应该创建全局分类。

### 7.3 C 端

| 页面 | 展示什么 | 使用接口 |
|---|---|---|
| 首页入口 | 经营分类 | `/api/v1/business-types` |
| 门店列表筛选 | 经营分类 | `/api/v1/stores?business_type=xxx` 或 `/api/v1/stores/nearby` |
| 进店点餐页左侧 | 门店菜单分类 | 建议使用带 `store_menu_category_id` 分组的菜单接口 |
| 搜索菜品 | 可用全局分类辅助筛选 | `/api/v1/categories?business_type=xxx` |

C 端首页不要展示“招牌锅贴、饮品饮料”这类门店菜单分类作为平台主入口。

## 9. 字段命名建议

当前代码里 `menu_items.category_id` 实际表示全局分类 ID。为了降低误解，建议前后端文档统一这样解释：

| 当前字段 | 推荐业务含义 | 是否建议改名 |
|---|---|---|
| `stores.business_types` | 门店已开通经营分类数组 | 不改 |
| `menu_items.business_type` | 菜品所属经营分类 | 不改 |
| `menu_items.category_id` | 菜品所属全局分类 ID | 中长期可改名为 `global_category_id` |
| `menu_items.store_menu_category_id` | 菜品所属门店菜单分类 ID | 不改 |
| `menu_categories.business_type` | 全局分类适用的经营分类 | 不改 |
| `menu_categories.store_id` | `0` 表示全局分类 | 中长期可拆表或去掉门店历史语义 |

短期不建议强行改数据库字段，因为会影响接口、迁移和历史数据。短期先在 DTO、文档、前端变量名里明确：`category_id = global_category_id`。

## 10. 删除和修改规则

### 10.1 经营分类

| 操作 | 规则 |
|---|---|
| 修改名称 | 允许，前端展示跟随变化 |
| 修改 code | 不建议允许，code 是业务稳定标识 |
| 停用 | 停用后新门店不可选择，已有门店可保留但不建议新建相关菜品 |
| 删除 | 如果被门店、菜品、全局分类引用，应拒绝 |

### 10.2 全局分类

| 操作 | 规则 |
|---|---|
| 修改名称 | 允许，影响后台和筛选展示 |
| 修改 business_type | 谨慎，若已有菜品引用，可能造成分类不匹配 |
| 停用 | 前端创建菜品时不展示 |
| 删除 | 如果已有菜品引用，必须拒绝或先迁移菜品 |

### 10.3 菜单分类

| 操作 | 规则 |
|---|---|
| 修改名称 | 允许，只影响本店点餐页 |
| 修改排序 | 允许，影响点餐页左侧顺序 |
| 删除 | 如果有菜品引用，建议先提示迁移到其他菜单分类 |
| 停用 | 可作为软删除方案，比硬删除更安全 |

### 11.1 总控前端

| 门店创建编辑 | `business_types` 使用多选，选项来自 `/admin/business-types` |

### 11.2 门店前端

菜品表单建议分三段：

| 区域 | 字段 | 来源 |

| 业务归属 | `business_type` | 当前门店 `business_types` |
| 平台归属 | `category_id` | `/api/v1/menu/categories?business_type=xxx` |

交互建议：

| 进店点餐 | 用门店菜单分类展示左侧分组 |
| 菜品搜索 | 可用全局分类做高级筛选 |

| 用例 | 操作 | 预期 |

## 13. 最终推荐口径

系统内所有人都按下面口径沟通：

| 说法 | 指的是 | 不要再混用成 |
|---|---|---|
| 经营分类 | `business_types`，门店经营范围 | 菜品分类 |
| 全局分类 | `menu_categories(store_id=0)`，平台标准菜品分类 | 门店菜单分组 |
| 菜单分类 | `store_menu_categories`，门店点餐页分组 | 平台经营入口 |

最终业务规则：

| 规则 | 说明 |
|---|---|
| C 端首页看经营分类 | 用户先找店，不是先看门店菜单 |
| 门店进店页看菜单分类 | 用户进店后才看“招牌、饮品、套餐” |
| 菜品必须绑定全局分类 | 平台需要标准化规则、报表、营销、搜索 |
| 菜品建议绑定菜单分类 | 门店需要灵活组织点餐页 |
| 总控管理经营分类和全局分类 | 平台治理口径统一 |
| 门店管理自己的菜单分类 | 门店经营展示灵活 |

## 14. 之前方案的主要弊端

之前的问题不是单个接口写错，而是分类模型没有分层，导致“找店、管菜、点餐展示”三件事都压在同一套分类上。短期能跑，长期一定乱。

### 14.1 弊端一：C 端首页把菜品分类当成经营入口

旧逻辑中，C 端首页或筛选容易使用 `/api/v1/categories`、`/api/v1/public/categories` 这一类菜品分类接口。

结果是首页可能展示：

| 展示内容 | 实际含义 | 问题 |
|---|---|---|
| 招牌锅贴 | 门店菜单分组 | 用户不是来首页找“锅贴分组”的 |
| 饮品饮料 | 菜单分类 | 不能代表一家门店的经营类型 |
| 热销套餐 | 门店运营分组 | 不适合作为平台级入口 |
| 火锅套餐 | 菜品标准分类 | 和“火锅店”不是一个概念 |

正确的首页入口应该是：

| 展示内容 | 实际含义 |
|---|---|
| 火锅 | 找火锅类门店 |
| 麻辣烫 | 找麻辣烫类门店 |
| 海鲜面 | 找海鲜面门店 |
| 民宿 | 找住宿门店 |

如果首页继续走菜品分类，用户会混淆“我要找店”和“我要看菜”。这就是业务入口错层。

### 14.2 弊端二：门店自己改分类会影响平台规则

如果门店菜单分类和平台全局分类混用，门店可以创建或修改类似下面的分类：

| 门店自定义分类 | 平台可能依赖它做什么 | 风险 |
|---|---|---|
| 招牌推荐 | 优惠券适用范围 | 名称不统一，规则难匹配 |
| 老板推荐 | 报表统计 | 统计口径不稳定 |
| 今日特价 | 搜索筛选 | 每个门店命名不同，无法统一筛选 |
| 网红必点 | 拼团商品归类 | 营销规则无法复用 |

平台规则需要稳定分类，门店展示需要灵活分类。把两者混在一起，会让平台无法做统一规则。

### 14.3 弊端三：菜品 `category_id` 来源不稳定

旧方案里，`menu_items.category_id` 可能引用全局分类，也可能引用历史门店分类。

这会导致：

| 场景 | 可能问题 |
|---|---|
| C 端按分类查菜 | 有些菜查不到 |
| 门店创建菜品 | 选到了不属于本业务的分类 |
| 总控删除分类 | 误删门店正在用的分类 |
| 报表按分类统计 | 同类菜品被拆到多个分类 |
| 优惠券按分类适用 | 同样的菜有些享受优惠，有些不享受 |

所以现在后端已经明确校验：`menu_items.category_id` 必须引用 `menu_categories.store_id=0` 的全局分类。

### 14.4 弊端四：经营分类写死会限制总控运营

如果 `business_types` 在前端写死，后续总控新增业务会变成发版问题。

例如新增：

| 新业务 | 如果前端写死会怎样 |
|---|---|
| 泰式烧烤 | 总控配置了，前端看不到 |
| 夜宵小吃 | 后端支持了，C 端无法筛选 |
| 民宿早餐 | 门店能配置，前端无法展示 |
| 旅游套餐 | 每端都要改代码发版 |

经营分类应该由总控管理，前端动态读取。否则每新增一个业务都要改三端代码，运营效率会很低。

### 14.5 弊端五：进店点餐页缺少门店自己的展示能力

如果只有全局分类，没有门店菜单分类，那么点餐页只能按平台分类展示。

例如平台全局分类只有：

| 全局分类 |
|---|
| 火锅套餐 |
| 火锅计件 |
| 饮品 |

但门店实际想展示：

| 门店菜单分类 |
|---|
| 招牌推荐 |
| 双人套餐 |
| 本周新品 |
| 饮品饮料 |
| 加料专区 |

没有 `store_menu_categories`，门店就不能像美团商家那样灵活组织自己的菜单页。最终点餐页会很僵硬，不利于提升转化。

### 14.6 弊端六：纯民宿和餐饮能力容易串台

如果只用一套分类，纯民宿门店可能被错误展示餐饮菜单分类，餐饮门店也可能看到民宿房型相关分类。

错误表现：

| 门店类型 | 错误展示 |
|---|---|
| 纯民宿 | 展示“火锅套餐、麻辣烫、饮品” |
| 火锅店 | 展示“民宿房间、房型、入住套餐” |
| 咖啡民宿 | 不知道是按住宿筛选还是按咖啡筛选 |

经营分类拆出来后，可以通过 `business_types` 控制门店能力。纯民宿只展示民宿相关功能，餐饮门店只展示餐饮相关功能。

## 15. 为什么要改成现在这套方案

### 15.1 改造目标

这次改造的目标不是“多加几张表”，而是把业务边界拆清楚。

| 目标 | 说明 |
|---|---|
| 平台能管 | 总控可以统一管理经营分类和全局分类 |
| 门店能调 | 门店可以自由调整自己的点餐页菜单分组 |
| C 端能懂 | 用户在首页看到的是经营入口，进店后看到的是菜单分组 |
| 报表能算 | 平台可以按稳定的经营分类和全局分类统计 |
| 规则能配 | 优惠券、拼团、搜索、推荐可以依赖稳定分类 |
| 后续能扩 | 新增业务时不需要三端硬编码发版 |

### 15.2 为什么经营分类必须独立

经营分类回答的是：这家店经营什么。

它决定：

| 影响范围 | 说明 |
|---|---|
| 门店准入 | 总控给门店开通哪些业务 |
| C 端首页 | 用户按业务类型找门店 |
| 门店功能 | 是否展示菜品、房型、拼团、民宿概览 |
| 菜品创建 | 菜品 `business_type` 必须属于门店已开通业务 |
| 统计报表 | 按火锅、麻辣烫、民宿等维度汇总 |

如果没有独立经营分类，系统就无法判断一家店到底是什么店，只能从菜品分类里猜。这个做法不可靠。

### 15.3 为什么全局分类必须由总控管理

全局分类回答的是：这个菜品在平台标准体系里属于什么。

它适合做：

| 用途 | 说明 |
|---|---|
| 平台统一报表 | 统计火锅套餐、饮品、麻辣烫等销售额 |
| 营销规则 | 配置某一类菜品可用优惠券 |
| 拼团规则 | 限定哪些标准分类商品可参加拼团 |
| 搜索筛选 | 用户搜某类商品时能跨门店统一返回 |
| 数据治理 | 避免每个门店随便命名导致统计失真 |

所以全局分类不能交给门店随便改。门店可以有自己的展示分组，但平台归属必须稳定。

### 15.4 为什么菜单分类必须给门店管理

菜单分类回答的是：这个菜在本店点餐页放哪里。

它适合做：

| 用途 | 说明 |
|---|---|
| 点餐页左侧分类 | 类似美团进店后的左侧菜单 |
| 门店运营排序 | 招牌、推荐、新品、套餐可以灵活排 |
| 本店特色表达 | 每家店都可以有自己的分类名 |
| 提升转化 | 门店可以把高毛利、高销量商品放在更前面 |

如果只用总控全局分类，门店点餐页会被平台分类绑死，运营空间太小。

### 15.5 为什么菜品需要同时绑定三类信息

菜品同时绑定 `business_type`、`category_id`、`store_menu_category_id` 是合理的，因为它们解决不同问题。

| 字段 | 解决的问题 | 示例 |
|---|---|---|
| `business_type` | 这个菜属于哪条业务线 | `HOTPOT_BUFFET` |
| `category_id` | 这个菜的平台标准分类是什么 | 火锅套餐 |
| `store_menu_category_id` | 这个菜在本店菜单页放哪里 | 招牌推荐 |

同一个菜品：

```json
{
  "name": "招牌牛肉火锅",
  "business_type": "HOTPOT_BUFFET",
  "category_id": 101,
  "store_menu_category_id": 8
}
```

业务含义：

| 字段 | 含义 |
|---|---|
| `business_type=HOTPOT_BUFFET` | 它属于火锅自助业务 |
| `category_id=101` | 它在平台标准分类里是火锅套餐 |
| `store_menu_category_id=8` | 它在本店页面放到招牌推荐 |

这不是重复字段，是三个不同维度。

### 15.6 改造后的收益

| 角色 | 收益 |
|---|---|
| 总控 | 可以统一管理平台经营入口和标准分类 |
| 门店 | 可以自由配置自己的点餐页菜单 |
| C 端用户 | 首页找店清楚，进店点餐清楚 |
| 后端 | 校验链路清晰，数据不再乱引用 |
| 前端 | 页面职责清楚，不同页面调用不同接口 |
| 测试 | 可以按经营分类、全局分类、菜单分类分别验收 |
| 运营 | 新增经营业务不需要频繁三端发版 |

### 15.7 不改会怎样

如果继续沿用旧方案，后续会出现这些必然问题：

| 问题 | 影响 |
|---|---|
| 首页分类越来越乱 | 用户找不到想要的门店 |
| 门店菜单无法个性化 | 点餐转化下降 |
| 报表分类不准 | 总控无法判断哪个业务赚钱 |
| 优惠券适用范围混乱 | 用户和商家都会投诉 |
| 拼团商品归属不稳定 | 拼团统计和库存控制容易出错 |
| 新业务上线成本高 | 每新增一个业务都要改三端 |
| 历史分类越来越脏 | 后期迁移成本指数上升 |

### 15.8 最终判断

这次改造是必要改造，不是过度设计。

原因很简单：平台型业务里，“商家经营什么”“商品平台归类”“商家页面怎么展示”天然就是三件事。美团、外卖、电商、酒店平台都会拆这三层，只是命名不同。

SiamFeast 当前已经开始覆盖餐饮、民宿、拼团、积分商城、优惠券、报表统计。如果还用一套分类硬撑，后续每个新功能都会继续踩同一个坑。
