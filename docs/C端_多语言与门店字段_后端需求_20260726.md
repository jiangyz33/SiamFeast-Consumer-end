## 一、需求背景

本次 C 端在多语言适配和门店信息展示上发现两类问题，需要后端配合补字段或对齐字段规范。前端已按"读后端多语言字段"的方式重构，**后端补字段前订单类型 tag 不显示**（既不是中英泰任何一种，纯空），等后端补齐即可恢复。

## 二、问题 1：订单类型未下发多语言文案（P1）

### 2.1 现象

订单列表页和订单详情页，订单类型标签（如「海鲜面 / Seafood Noodles / ก๊วยเตี๋ยวทะเล」）直接显示成**原始英文枚举值**：

```
[SEAFOOD_NOODLES]   ← 实际显示
[海鲜面]            ← 期望显示
```

### 2.2 根因

- 后端 `order.order_type` 下发的是业务枚举（`SEAFOOD_NOODLES` / `HOTPOT` / `MALA_TANG` / `BEVERAGE` / `DINE_IN` / `DELIVERY` / `PICKUP` / `GROUP_BUY` 等）
- **没有下发对应的展示文案**
- 前端原本硬编码了一份 `ORDER_TYPE_I18N` 映射表兜底，但：
  - 后端枚举命名不统一（`SEAFOOD_NOODLE` vs `SEAFOOD_NOODLES`，`MALATANG` vs `MALA_TANG`）
  - 新增业务类型时前端永远追不上
  - 已移除硬编码，改为**只读后端多语言字段**

### 2.3 涉及接口

- `GET /api/v1/user-orders/my-orders`（订单列表）
- `GET /api/v1/user-orders/{id}`（订单详情）

### 2.4 期望返回字段

在每个 order 对象中**新增三个字段**（命名遵循项目现有的 `item_name_en` / `store_name_en` 多语言约定）：

| 字段 | 类型 | 必填 | 示例 |
|---|---|---|---|
| `order_type_name` | string | 是 | `"海鲜面"` |
| `order_type_name_en` | string | 是 | `"Seafood Noodles"` |
| `order_type_name_th` | string | 是 | `"ก๊วยเตี๋ยวทะเล"` |

返回示例：

```json
{
  "id": 1234,
  "order_no": "SF202607261234",
  "order_type": "SEAFOOD_NOODLES",
  "order_type_name": "海鲜面",
  "order_type_name_en": "Seafood Noodles",
  "order_type_name_th": "ก๊วยเตี๋ยวทะเล",
  "status": "COMPLETED",
  "...": "其他字段保持不变"
}
```

### 2.5 文案参考表（建议后端建 i18n 文案字典）

| order_type 枚举 | 中文 | 英文 | 泰文 |
|---|---|---|---|
| `SEAFOOD_NOODLES` / `SEAFOOD_NOODLE` / `SINEFOOD_NOODLE` | 海鲜面 | Seafood Noodles | ก๊วยเตี๋ยวทะเล |
| `HOTPOT` / `BBQ` | 火锅 | Hotpot | หม้อไฟ |
| `MALATANG` / `MALA_TANG` | 麻辣烫 | Malatang | มาลาทัง |
| `BEVERAGE` | 饮品 | Beverage | เครื่องดื่ม |
| `DINE_IN` | 堂食 | Dine-in | ทานที่ร้าน |
| `TAKEAWAY` / `PICKUP` | 自提 | Pickup | รับเอง |
| `DELIVERY` | 外送 | Delivery | จัดส่ง |
| `GROUP_BUY` | 团购 | Group Buy | กลุ่มซื้อ |

> 后端维护一份枚举→文案的字典，**统一兼容历史枚举命名**（如同时支持 `SEAFOOD_NOODLE` 和 `SEAFOOD_NOODLES`）。

### 2.6 前端读取逻辑（已实现，无需再改）

```js
order['order_type_name_' + lang] || order.order_type_name || ''
// lang 取值：zh / en / th
```

后端补字段前，订单类型 tag 不会显示（既不是英文也不是中文，纯空）—— 这是预期行为。

## 三、问题 2：门店营业时间字段缺失/不一致（P2）

### 3.1 现象

- 门店详情页能显示营业时间，但很多门店**显示成 `-`**（占位符）
- 堂食门店列表页（dinein-stores）**完全看不到营业时间**

### 3.2 根因

1. **门店详情接口** `GET /api/v1/stores/{id}`：
   - 返回了 `business_hours` 字段，但**值是字符串 `"-"`**（占位/空值），而非真实时间
   - 缺少 `config.opening_time` / `config.closing_time`（前端首选字段）

2. **门店列表接口** `GET /api/v1/public/stores`：
   - 列表项里**完全没有营业时间字段**

3. **字段命名不统一**：前端目前兼容了 6+ 种字段组合作为兜底，但只要后端任何一种形态都没真实数据，前端就显示不出。

### 3.3 涉及接口

- `GET /api/v1/stores/{id}`（门店详情）
- `GET /api/v1/public/stores`（门店列表，C 端公共接口）
- `GET /api/v1/stores/nearby`（附近门店，若存在）

### 3.4 期望字段规范（统一）

**推荐方案**：所有门店接口在 store 对象中**统一下发以下字段**（任选一组即可，前端会自动读取）：

#### 方案 A（推荐）：config 嵌套 + 24 小时标记

```json
{
  "id": 1,
  "name": "...",
  "config": {
    "opening_time": "11:00:00",
    "closing_time": "22:00:00",
    "is_24_hours": false
  }
}
```

#### 方案 B：顶层 business_hours 字符串

```json
{
  "id": 1,
  "name": "...",
  "business_hours": "11:00-22:00"
}
```

> **二选一，全项目统一**。建议方案 A，因为信息更完整（支持 24 小时营业标记、更结构化）。

### 3.5 关键要求

1. **列表接口也要返回营业时间字段**：`/public/stores` 当前没下发，必须补上。
2. **不要用占位符**：未配置营业时间的门店，对应字段返回 `null` 或空字符串 `""`，**不要返回 `"-"`**（前端会按"有数据"渲染但显示成短横线，误导用户）。
3. **24 小时营业**：如果走方案 A，`is_24_hours: true` 时前端会显示 `24h`。

### 3.6 前端读取逻辑（已实现，支持多种字段兜底）

```js
// 优先读 config.opening_time/closing_time
// 其次读 business_hours 字符串
// 再次读顶层 opening_time/closing_time
// 最后检查 is_24_hours → 显示 "24h"
```

## 四、问题 3：订单规格信息（specs）保留与回显（P2）

### 4.1 现象

带规格的商品（如选了"大份/中辣/+芝士"的菜品）下单后，订单详情能正常显示，但**"再来一单"功能丢规格**。

### 4.2 涉及接口

- `GET /api/v1/user-orders/{id}`（订单详情，需要返回完整 specs）

### 4.3 期望返回字段

`order.items[*]` 中每个 item 需保留下单时传入的 specs 信息：

```json
{
  "items": [
    {
      "item_id": 101,
      "item_name": "海鲜面",
      "item_name_en": "Seafood Noodles",
      "item_name_th": "ก๊วยเตี๋ยวทะเล",
      "quantity": 1,
      "unit_price": 120,
      "specs": {
        "spec": { "id": 1, "name": "大份", "price_diff": 20 },
        "flavor": { "id": 5, "name": "中辣", "price_diff": 0 },
        "toppings": [
          { "id": 11, "name": "加芝士", "price_diff": 10 }
        ]
      },
      "...": "其他字段"
    }
  ]
}
```

### 4.4 关键要求

- **specs 字段名固定为 `specs`**（不要用 `specs_config`、`spec_list` 等变体）
- **specs 内的 name 字段需要支持多语言**：建议在每个 spec 项里同时下发 `name` / `name_en` / `name_th`，或在订单查询时按 `Accept-Language` 返回对应语言。

> 前端目前 specs 结构是 `{ spec: {id,name,price_diff}, flavor: {...}, toppings: [{...}] }`，**与下单时上送的结构保持一致**即可。
